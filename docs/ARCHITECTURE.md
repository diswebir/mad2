# قرارداد ماژول و توسعه

## رجیستری واحد

`shared/catalog.js` منبع نام، آیکون، فیلدها، نقش‌های read/write، کلید ماژول و capability است. تعریف منابع به‌صورت whitelist در API استفاده می‌شود. چهار عمل CRUD برای هر منبع، چهار capability مستقل هستند و این تعریف دقیق مبنای عدد ۱۳۴ است.

## لایهٔ داده

- `server/database.js`: موتور SQLite/WASM با SQL.js، شاخص‌های رابطه/تاریخ، foreign key، transaction همگام، export و نوشتن اتمیک.
- `DATA_DIR/school.sqlite`: بانک خصوصی. هر تغییر ماندگار می‌شود، صرفاً mock در localStorage نیست.
- `DATA_DIR/school.lock`: مالکیت تک‌فرآیندی؛ هر فرآیند مستقل حافظهٔ متفاوتی دارد و نباید هم‌زمان writer باشد.
- `DATA_DIR/uploads`: محتوای فایل؛ جدول files فقط metadata و نام ذخیره را دارد.
- export در SQL.js اتصال را بازمی‌سازد؛ `db.export()` بعد از آن PRAGMA foreign_keys را دوباره فعال می‌کند. کد جدید نباید مستقیم از `db.raw.export()` استفاده کند.

## هم‌زمانی و یکپارچگی

- هر رکورد یک ستون `revision` دارد؛ ویرایش/حذف با نسخهٔ قدیمی خطای `STALE_RECORD` می‌دهد تا دو مدیر هم‌زمان روی هم بازنویسی نکنند.
- رکوردهای وابسته به دورهٔ آموزشی (نمره، حضور) کلاسِ هنگام ثبت را نگه می‌دارند و پس از جابه‌جایی دانش‌آموز، تاریخچه جابه‌جا نمی‌شود.
- فایل آپلودی زمینهٔ مصرف (`tickets`, `documents`, `assignments`, `submission`) را در پایگاه‌داده ذخیره می‌کند و فقط در همان گردش‌کار قابل استناد است.
- اعلان اطلاعیه‌ها با نشانهٔ تراکنشی `notified_at` دقیقاً یک‌بار به هر عضو واجد شرایط تحویل می‌شود؛ Passenger که بین درخواست‌ها می‌خوابد با اولین درخواست بعدی تحویل را انجام می‌دهد.
- مهاجرت‌ها افزایشی‌اند: ستون‌های تازه (`revision`، `context`، `notified_at`، `class_id` نمرات) روی پایگاه‌دادهٔ موجود اضافه و مقادیر قدیمی بازسازی می‌شوند.

## دسترسی

مراحل اجرای هر عمل:

1. نشست معتبر، حساب فعال و رمز غیرموقت.
2. ماژول و capability فعال.
3. نقش خواندن/نوشتن مجاز.
4. scope رکورد/کلاس مجاز، حتی با حدس شناسه در URL.
5. اعتبارسنجی فیلد و قواعد تجاری.
6. تراکنش، audit و پاسخ.

معلم به کلاس‌های معلم راهنما یا زنگ‌های تخصیص‌یافته دسترسی دارد. دانش‌آموز/ولی به students.id متصل در users.student_id محدود است. تیکت به sender_id / recipient_id و مدیر محدود می‌شود؛ حساب ولی به‌طور خودکار مجوز خواندن تیکت خصوصی فرزند ندارد.

## APIهای اصلی

- `/api/auth/*`: ورود، نشست، خروج، پروفایل و رمز.
- `/api/setup`: آمادگی عمومی و نصب توکن‌دار یک‌باره.
- `/api/entities/:resource`: CRUD / جست‌وجو / فیلتر / صفحه‌بندی منابع ثبت‌شده.
- `/api/attendance`: ثبت دسته‌ای و گزارش روز؛ history مستقل.
- `/api/tickets`: inbox، پیام و وضعیت خصوصی.
- `/api/assignments/:id`: تحویل و ارزیابی.
- `/api/files`: بارگذاری contextدار و دریافت مجاز.
- `/api/settings/*`: مدرسه، ماژول، capability، حساب، reset، audit و backup.
- `/api/config`, `/api/lookups`: پیکربندی و برچسب‌های حداقلی انتخاب‌گرها.
- `/api/dashboard`, `/api/reports`, `/api/calendar`, `/api/search`, `/api/notifications`: نماهای مجاز و محاسبه‌شده.

## افزودن منبع یا ماژول

1. moduleDefs و resourceDefs و moduleGroups را با شناسهٔ ثابت و فیلدهای معتبر گسترش دهید.
2. برای CRUD عمومی، جدول/فرم/کلیدها از رجیستری ساخته می‌شوند. رابطه‌ها فقط به منابع ثبت‌شده باشند.
3. در `security.scope` منابع شخصی جدید را محدود کنید؛ پیش‌فرض public-school برای دادهٔ شخصی مناسب نیست.
4. قواعد مالی/زمان/موجودی را در businessRules و hook تراکنش ثبت کنید، نه فقط در React.
5. برای workflow اختصاصی Router و صفحهٔ جدا بسازید و capability جدید را در API بررسی کنید.
6. مهاجرت schema برای تغییر جدول موجود را صریح بنویسید. ساخت خودکار اولیه جای migration ستون‌های یک نصب قدیمی را نمی‌گیرد.
7. آزمون مجوز، rollback، خاموش‌شدن capability و UI اضافه کنید؛ `npm run features` فهرست عمومی را بازتولید می‌کند.

## قابلیت‌های وابسته

- هر قابلیت افزون بر نقش، می‌تواند `requires` داشته باشد؛ مثلاً `attendance.export` بدون `attendance.view` و `students.profile` بدون `students.view` در دسترس نیست. همین قواعد در سرور و رابط یکسان اعمال می‌شوند.
- فعال/غیرفعال‌بودن حساب کاربری و وضعیت پروندهٔ مرتبط دو دروازهٔ مستقل‌اند: حساب دستی‌غیرفعال با ویرایش پرونده روشن نمی‌شود و حساب بدون پروندهٔ فعال وارد نمی‌شود.

## مسیر رشد

نسخهٔ اول تک‌مدرسه‌ای است و مدل tenant، connection pool چند worker، job queue و adapter MySQL ندارد. برای توسعهٔ چندمدرسه‌ای ابتدا tenant_id و row isolation در همهٔ جداول، سپس adapter تراکنش و storage فایل مشترک طراحی شود. تقویت آزمون بار و ممیزی قبل از ورود دادهٔ واقعی در هر مقیاس ضروری است.
