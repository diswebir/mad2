# فروش ماژولار: قیمت‌گذاری، صدور لایسنس و کنترل ماژول‌ها

این سند دو بخش دارد: **۱) مدل کسب‌وکار و روش فروش** و **۲) ابزار فنی لایسنس** که همین حالا در سامانه پیاده شده است. مدل انتخابی شما — **بدون اشتراک، لایسنس مادام‌العمر برای همان نسخه** — در این ساختار پشتیبانی می‌شود.

---

## ۱) مدل فروش: قیمت پایه + ماژول

### چرا این مدل درست است

- مدرسهٔ کوچک با «حضور، نمره، پرونده» راضی می‌شود و ورودش ارزان است؛ همان مدرسه بعداً با فروش یک ماژول (مالی، پیامک، کتابخانه) درآمد تازه می‌سازد.
- هر ماژول را می‌توانی جدا قیمت بگذاری و تخفیف بسته بدهی، بدون تغییر کد.
- چون اشتراک نمی‌فروشی، درآمد یک‌باره است؛ پس باید **قیمت پایه را واقع‌بینانه بالا بگیری**، **دورهٔ پشتیبانی را محدود کنی** و **درآمد بعدی را از ماژول‌های افزودنی و ارتقای نسخه بسازی**.

### پیشنهاد تقسیم ماژول‌ها

| گروه                         | ماژول‌ها                                                                                                                                                                         | منطق                                                               |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| **پایه (در قیمت پایه)**      | `dashboard`، `students`، `teachers`، `classes`، `attendance`، `education`، `tickets`، `announcements`، `calendar`، `notifications`، `profile`، `settings` — ۱۲ ماژول، ۱۲۹ قابلیت | هستهٔ حیات مدرسه؛ اگر نباشد سامانه بی‌معنی است و پشتیبانی‌اش دردسر |
| **افزودنی پرطرفدار**         | `finance` (۱۴ قابلیت: شهریه، تخفیف، اقساط، جریمه، بدهکاران، حقوق)                                                                                                                | مستقیم پول مدرسه را مدیریت می‌کند؛ خریدار آماده است                |
| **افزودنی**                  | `reports` (۱۳: کارنامه، روند، وزارتی، ارتقا، چاپ، xlsx)                                                                                                                          | مدرسهٔ ضعیف بی‌نیاز است؛ دبیرستان‌ها مشتری فوری‌اند                |
| **افزودنی**                  | `library` (۱۵)، `meetings` (۱۰)، `services` (۱۲)                                                                                                                                 | بستهٔ زندگی مدرسه؛ سه‌تایی بفروش تا راحت‌تر                        |
| **قابلیت‌های خارج از ماژول** | `settings.messaging` (پل پیامک/ایمیل)، `settings.restore`، `settings.status`، `support.report`                                                                                   | می‌توانی «بستهٔ پشتیبانی بیرونی» را جدا قیمت بگذاری                |

| بستهٔ پیامک/ایمیل                        | ۴ تا ۶ میلیون            | جدا از هزینهٔ سرویس‌دهندهٔ پیامک                      |

> عددها را با دو سه مدرسه واقعی آزمون کن؛ اگر همه بدون چانه‌زدن قبول کردند، پایه را بالا ببر.

### شرایطی که باید در قرارداد بنویسی (مادام‌العمر یعنی چه)

«لایسنس مادام‌العمر» را دقیق تعریف کن، وگرنه ده سال بعد گرفتار می‌شوی:

1. **حق استفاده دائمی** از همان نسخهٔ تحویل‌شده، روی یک مدرسه و یک نصب.
2. **پشتیبانی و به‌روزرسانی رایگان: ۱۲ ماه** از تاریخ تحویل (شامل رفع اشکال و به‌روزرسانی‌های کوچک `1.x`).
3. **نسخه‌های بزرگ بعدی رایگان نیستند**؛ ارتقا اختیاری و با تخفیف.
4. **بدون هزینهٔ سالانه و بدون هزینهٔ سرانهٔ دانش‌آموز** — این را در پیشنهادت پررنگ کن؛ برای مدیر مدرسه جذاب‌ترین بخش است.
5. پیامک، دامنه، SSL و هاست هزینهٔ خود مدرسه است.
6. دادهٔ مدرسه مال مدرسه است؛ تحویل فایل `.sqlite` و پشتیبان‌گیری در اختیار آن‌هاست.
7. ممنوعیت واگذاری/فروش مجدد لایسنس، و **نام مدرسه روی لایسنس** ثبت می‌شود (سریال اختصاصی).

### گردش کار فروش (۱۱ قدم)

1. **نمایش:** لینک دمو را بفرست (نسخهٔ دموی خودت یا `npm run package:demo` روی یک زیردامنه).
2. **نیازسنجی:** سه سؤال بپرس — چند دانش‌آموز؟ چند شعبه؟ شهریه و کتابخانه دستی است؟ پشتیبانی با این پاسخ‌ها خودش مشخص می‌شود.
3. **پیشنهاد قیمت:** فهرست ماژول‌ها + جمع، به‌صورت جدول (قالب آماده در بخش ۳).
4. **قرارداد و پیش‌پرداخت:** معمولاً ۵۰٪ پیش، ۵۰٪ تحویل.
5. **صدور لایسنس:**

   ```bash
   npm run license:issue -- --customer "دبستان شهید الف" --edition standard --modules meetings,library --key ./license-keys/license-private.pem --out ./license-keys/MY-1405-0007.json
   ```

6. **تحویل:** ZIP بستهٔ cPanel + فایل `license.json` + راهنمای [CPANEL-INSTALL.md](CPANEL-INSTALL.md).
7. **نصب:** خودت نصب کن (بهترین حالت) یا مدرسه با راهنما نصب کند و تو با AnyDesk کمک کنی.
8. **ورود اطلاعات پایه:** کلاس‌ها، دانش‌آموزان، برنامهٔ هفتگی (خدمات پرداختی).
9. **آموزش:** یک جلسه برای مدیر و یک جلسه برای معلم‌ها.
10. **پشتیبان اول:** از پنل مدرسه پشتیبان بگیر و مسیر بازیابی را یک‌بار آزمایش کن.
11. **ثبت در دفتر لایسنس** (بخش ۴) و یادآور پشتیبانی پس از ۱۲ ماه.

### فروش ماژول بعدی به مشتری قدیمی

درآمد بعدی‌ات همین است. وقتی مدرسه می‌گوید «کتابخانه هم می‌خواهیم»:

1. پرداخت را بگیر.
2. **همان سریال، ماژول بیشتر:** لایسنس تازه با فهرست کامل ماژول‌های خریداری‌شده صادر کن (سریال یکسان بماند).

   ```bash
   npm run license:issue -- --id MY-1405-0007 --customer "دبستان شهید الف" --edition complete --key ./license-keys/license-private.pem --out ./license-keys/MY-1405-0007-v2.json
   ```

3. فایل را روی هاست در `DATA_DIR/license.json` جایگزین کن و برنامه را Restart کن. **هیچ داده‌ای پاک نمی‌شود؛ فقط کلید آن ماژول باز می‌شود.**

## ۲) ابزار لایسنس (پیاده‌شده در همین نسخه)

اصل طراحی: **بدون تماس با سرور تو.** لایسنس با کلید خصوصی تو امضا می‌شود و روی هاست مدرسه فقط با کلید عمومی بررسی می‌شود؛ پس مدرسهٔ بدون اینترنت هم کار می‌کند و تو لازم نیست سرویس آنلاین نگه داری.

### راه‌اندازی یک‌باره (روی سیستم خودت)

```bash
npm run license:keygen -- --out ./license-keys
```

خروجی:

- `license-keys/license-private.pem` → **این را محرمانه نگه دار.** در مخزن Git، ایمیل یا سرور مشتری نگذار.
- `license-keys/license-public.pem` → این را در نسخه‌ای که می‌فروشی قرار بده (خط آخر بخش «نصب کلید عمومی»).

### کارهای روزمره

```bash
npm run license:list                                   # فهرست ماژول‌ها و بسته‌های آماده
npm run license:issue -- --customer "دبیرستان نمونه" --edition standard
npm run license:issue -- --customer "دبستان الف" --modules finance,library --note "شعبه مرکزی"
npm run license:inspect -- --license ./license-keys/MY-1405-0007.json
```

بستهٔ آماده (`--edition`) شامل: `base` (پایه)، `standard` (پایه + مالی + کتابخانه + گزارش‌ها)، `complete` (همه). با `--modules` ترکیب دلخواه بفروش و با `--features` می‌توانی تک‌قابلیت بفروشی (مثلاً فقط `settings.messaging`).

### نصب کلید عمومی روی نسخهٔ فروشی (یکی از دو راه)

**راه الف — فایل `.env` روی هاست مشتری (ساده‌ترین):**

```dotenv
LICENSE_MODE=on
LICENSE_PUBLIC_KEY="-----BEGIN PUBLIC KEY-----\n...\n-----END PUBLIC KEY-----"
```

**راه ب — جای‌گذاری دائمی پیش از بسته‌بندی:** مقدار `VENDOR_PUBLIC_KEY` را در `shared/license.js` از فایل `license-public.pem` پر کن و `npm run package:cpanel` بگیر. با این کار مشتری حتی لازم نیست کلید را تنظیم کند (فقط `LICENSE_MODE=on`).

### نصب لایسنس روی هاست مشتری

1. فایل `MY-...json` را در `DATA_DIR` با نام `license.json` بگذار (یا محتوایش را در `.env` به‌شکل `LICENSE_KEY="..."` قرار بده).
2. `LICENSE_MODE=on` را در `.env` بگذار.
3. Restart کن. در لاگ می‌بینی: `License: valid — ... (n modules)`.

### مدرسه چه چیزی می‌بیند

- صفحهٔ «ماژول‌ها»: ماژول‌های خریده‌نشده با نشان **«خریدنی»** و سوییچ غیرفعال؛ نوار بالای صفحه نام مشتری و سریال لایسنس را نشان می‌دهد.
- «تنظیمات → وضعیت سرویس»: کارت لایسنس با نام مشتری، سریال و تعداد ماژول.
- API: قابلیت‌های خارج از لایسنس با کد `LICENSE_REQUIRED` رد می‌شوند (نه فقط پنهان در UI).
- در پنل، تلاش برای فعال‌کردن ماژول نخریده هم با پیام روشن رد می‌شود؛ یعنی نه مدیر می‌تواند ماژول را باز کند، نه کاربر با URL مستقیم دور بزند.

### حالت‌ها

| `LICENSE_MODE`  | رفتار                                                                                                 |
| --------------- | ----------------------------------------------------------------------------------------------------- |
| `off` (پیش‌فرض) | همهٔ ماژول‌ها باز؛ برای توسعه، دمو و نسخهٔ خودمیزبان.                                                 |
| `on`            | فقط ماژول‌های لایسنس + ماژول‌های پایه. لایسنس نامعتبر/نبود → فقط پایه، با پیام علت روی `/api/status`. |

ماژول‌های **پایه** همیشه باز می‌مانند تا مدرسه با لایسنس ناقص قفل نشود؛ اگر می‌خواهی ترکیب «پایه» را برای نسخهٔ خودت عوض کنی، فقط فهرست `BASE_MODULES` در `shared/license.js` را تغییر بده و دوباره بسته‌بندی کن.

### چند مدرسه روی یک هاست

هر نصب، `DATA_DIR` و لایسنس جدا دارد (ساب‌دامنه یا زیرپوشه). برای هرکدام یک `license.json` متفاوت بگذار و در دفتر لایسنس ثبت کن.

## ۴) دفتر لایسنس و پشتیبانی

یک فایل ساده (مثلاً `license-registry.csv` بیرون از مخزن) نگه دار:

| سریال        | مشتری           | شهر | تاریخ      | بسته      | ماژول‌های افزودنی | نسخه  | پشتیبانی تا | یادداشت                |
| ------------ | --------------- | --- | ---------- | --------- | ----------------- | ----- | ----------- | ---------------------- |
| MY-1405-0007 | دبستان شهید الف | ... | 1405/07/09 | استاندارد | ملاقات، کتابخانه  | 1.1.0 | 1406/07/09  | سفارش کتابخانه در ۱۴۰۶ |

نکته‌ها:

- **سریال را یکتا نگه دار** و در لایسنس مشتری هم بمان؛ اگر لایسنسی جایی منتشر شد، از سریال می‌فهمی مال کدام مدرسه است.
- **تمام اعلان‌های ارسالی به خانواده‌ها می‌تواند نام مدرسه و سریال را در فوتر داشته باشد** (اختیاری) تا استفادهٔ غیررسمی زودتر لو برود.
- برای هر نصب، **پشتیبان اول را خودت بگیر**؛ بعدها «داده از دست رفته» پرتکرارترین تماس پشتیبانی است.
- یادآور ۳۰ روز قبل از پایان پشتیبانی: پیشنهاد تمدید + ماژول تازه.

## ۵) پیوست فنی: زنجیرهٔ تأیید لایسنس

خلاصهٔ آنچه در کد اتفاق می‌افتد، تا هر وقت لازم شد خودتان بازبینی کنید:

**الف) ساختار فایل لایسنس** (`shared/license.js`):

```json
{
  "alg": "ed25519",
  "payload": {
    "v": "1.1.0",
    "id": "MY-1405-5733",
    "customer": "دبیرستان نمونه",
    "edition": "custom",
    "modules": ["finance"],
    "features": ["settings.messaging"],
    "issued": "2026-10-01",
    "expires": "",
    "note": ""
  },
  "signature": "O4AE1+3i584ZQu64VuWdXzgtEBlDRK5hEotgAhnRn34s03/T6Eka...=="
}
```

- **چه چیزی امضا می‌شود؟** همان `payload` با ترتیب کلیدهای ثابت (`stableSerialize`) تا امضا در همهٔ نسخه‌های Node یکسان باشد.
- **با چه الگوریتمی؟** Ed25519 با `crypto.sign(null, payload, privateKey)`؛ تأیید با `crypto.verify(null, payload, publicKey, signature)`.
- **کلید خصوصی** فقط پیش فروشنده می‌ماند (`license-keys/license-private.pem`، پیشنهاد: روی فلش/مدیر رمز، نه در Git و نه روی سرور مشتری). **کلید عمومی** در نسخهٔ فروشی قرار می‌گیرد (`LICENSE_PUBLIC_KEY` در `.env` یا `LICENSE_PUBLIC_KEY_PATH` یا `VENDOR_PUBLIC_KEY` در `shared/license.js`).

**ب) لحظهٔ اجرا:**

1. `server/index.js` با `loadEntitlement({ dir: db.dir })` لایسنس را از این ترتیب می‌خواند: `LICENSE_KEY` (متن در `.env`) → `LICENSE_FILE` → `DATA_DIR/license.json` → `DATA_DIR/license.key`.
2. `resolveEntitlement` نتیجه را به یکی از حالت‌ها تبدیل می‌کند: `off` (همه باز)، معتبر، یا نامعتبر با دلیل مشخص: `LICENSE_MISSING`، `LICENSE_MALFORMED`، `LICENSE_SIGNATURE`، `LICENSE_ALGORITHM`، `LICENSE_EXPIRED`، `LICENSE_EMPTY`، `PUBLIC_KEY_MISSING`.
3. ماژول‌های **پایه** همیشه اضافه می‌شوند (حتی اگر در payload نباشند) و ماژول/قابلیت ناشناس در payload دور ریخته می‌شود.
4. در لاگ استارت یک خط چاپ می‌شود: `License: valid — … (n modules)` یا `License: not active — <دلیل>`.

**پ) چهار جایی که لایسنس اعمال می‌شود:**

| لایه                    | فایل                                                                      | رفتار                                                                         |
| ----------------------- | ------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| هر endpoint قابلیت‌محور | `server/security.js` → `feature(id)`                                      | اول `entitled` بعد `enabled`؛ رد با `403 LICENSE_REQUIRED`                    |
| فهرست‌های CRUD عمومی    | `server/resources.js` → `check()`                                         | همان بررسی برای `${resource}.${action}`                                       |
| تنظیمات مدیر            | `server/modules/settings.js`                                              | `PATCH /settings/modules/:id` و `/features/:id` ماژول نخریده را روشن نمی‌کند  |
| رابط کاربری             | `/api/config` (پرچم `entitled`) + `shared/catalog.js` و `src/context.jsx` | کارت «خریدنی»، سوییچ قفل، منو و مسیرهایی که API رد می‌کند نمایش داده نمی‌شوند |

**ت) خودآزمایی پیش از تحویل به مشتری:**

```bash
node scripts/license.mjs inspect --license ./license-keys/MY-1405-5733.json   # امضا معتبر؟ کدام ماژول‌ها؟
npm test -- tests/license.test.js                                             # ۷ آزمون امضا/دست‌کاری/انقضا/اعمال سه‌لایه
```

و آزمون دستی روی سرور (همان کاری که در ساخت این نسخه اجرا شد): سرور را با `LICENSE_MODE=on` و لایسنس «پایه + مالی» بالا بیاورید؛ سپس:

- `GET /api/finance/settings` → **۲۰۰** (ماژول خریداری‌شده)
- `GET /api/library/reservations` → **۴۰۳** با کد `LICENSE_REQUIRED` (ماژول نخریده)
- `PATCH /api/settings/modules/library` → **۴۰۳** (مدیر هم نمی‌تواند بازش کند)
- `GET /api/entities/students` → **۲۰۰** (پایه دست‌نخورده)
- فایل لایسنس را دست‌کاری کنید (مثلاً یک ماژول به payload اضافه کنید) → لاگ `License: not active — امضای لایسنس…` و همهٔ ماژول‌های افزودنی بسته می‌شوند، ولی سامانه با ماژول‌های پایه بالا می‌ماند.

## ۶) واقع‌بینانه دربارهٔ کپی و قفل

- این لایسنس **قفل سخت‌گیرانه نیست**؛ کسی که کلید خصوصی نداشته باشد نمی‌تواند لایسنس جعلی معتبر بسازد، اما مدیر فنی می‌تواند فایل را پاک کند و عملاً فقط پایه‌ها کار کنند. این عمدی است: مدرسه نباید سر اول سال با قفل‌شدن سامانه گرفتار شود.
- راه‌های واقعی که خودش محافظ است: **پشتیبانی و آموزش** (چیزی که کپی نمی‌شود)، **نام مشتری روی لایسنس**، **امضای Ed25519** و صدور نسخهٔ مخصوص هر مدرسه با نام/سریال.
- اگر مشتری پرتقاضای حساس داری، می‌توانی برایش نسخهٔ سفارشی با `BASE_MODULES` محدودتر بدهی؛ اما بند «بدون کپی مجدد» را در قرارداد بگذار، نه در کد.
- **رمزنگاری و مبهم‌سازی کد را عوض نکن**؛ وقت تلف می‌کند و مدرسه را از تعمیر نگه‌داری دور می‌کند.

## ۷) چرا مشتری این را می‌خرد (حرف فروش)

1. **یک‌بار بخر، همیشه داشته باش** — بدون هزینهٔ سالانه و بدون اجاره.
2. **داده روی هاست خود مدرسه است** — هیچ‌چیز جایی منتقل نمی‌شود.
3. **فارسی، راست‌به‌چپ، تاریخ شمسی** و فونت محلی؛ کار با آن برای مدیر و معلم ساده است.
4. **ماژولار:** فقط چیزی را بخر که لازم داری؛ بعداً اضافه کن.
5. **جدا شدن واقعی دسترسی‌ها:** ولی فقط فرزند خودش، معلم فقط کلاس‌های خودش.
6. **کارنامهٔ چاپی، پیامک به خانواده، بازیابی پشتیبان و کارهای امروز من** — همان چیزهایی که مدیر هر روز وقتش را می‌گیرد.
